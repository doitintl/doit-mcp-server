# Local deployment review and evidence

Keep source files, cloud credentials, Terraform state, plans and raw logs in the customer's environment. DoiT requirements are the expected access contract; a customer-produced preview is not server-verified evidence.

For Terraform, inspect the initialized provider/module versions and `terraform show -json` output from a saved plan. Compare planned identity and exact scopes, IAM trust/principal/External ID, permission/role grants and artifact parameters with the fresh requirements response. Examine `resource_changes` and `after_unknown`: unknown trust or permission values produce `planned_trust_unresolved`/`planned_permissions_unresolved`, never a passing review. Identify deletions/replacements and unrelated members or permissions removed from shared policies. Keep the provider's Cloud Connect registration resource authoritative. Apply the reviewed plan through the customer's normal gate.

For CloudFormation, inspect the actual template and change set parameters, resource replacements, IAM policies and hooks. Check the member targets of StackSets separately from the parent operation. Collect terminal stack/callback request references locally; callback HTTP success and CloudFormation response delivery are different observations.

For ARM/Bicep, use what-if at the exact deployment scope and inspect role definitions/assignment scope, tenant and principal. For gcloud/bq or Azure CLI sequences without reliable preview, prepare reviewable commands and describe what cannot be proved before execution. Preserve unrelated policy members; never replace an IAM policy from a partial listing.

Before an opt-in hosted diagnostic report, classify the local failure into the tool's bounded source, operation and code fields. Do not pass raw stderr, state, plan JSON, credentials, authorization headers, keys, tokens or arbitrary log messages as tool arguments. The tool constructs a fixed public message from that classification; the hosted schema has no message field. Customer reports are informational and cannot assert DoiT verification outcomes, health or approval.

A registration dry run previews backend effects and performs DoiT's live gate where the credential broker can probe without registration. New AWS roles have an explicit unsupported dry-run limitation described in the AWS reference; actual registration must still pass the live gate. It cannot validate a proposed cloud plan before that access exists. Treat a pre-deployment identity failure as an unmet live prerequisite; re-run after deployment rather than interpreting it as proof that the plan is wrong.
