# AWS

Bindings identify individual accounts. Organization roots and OUs can be deployment targets, but are not connection bindings. Use the requirement response's provider variant, payer association, identity trust and exact artifact parameters. Asset association and recognized management-account preconditions are DoiT prerequisites; creating a role alone cannot satisfy them.

Trust is environment-specific. `identity.trust` describes the baseline principal and External ID; an AWS artifact's `trustStatements` describes its complete cross-account `Allow sts:AssumeRole` policy. Each statement names an AWS principal and, when present, its required External ID. An omitted `externalId` means that statement is unconditional. Compare every statement with the rendered plan, including any additional development principals; do not assume the baseline identity describes all artifact grants. Surface unconditional or broader grants in the deployment review and preserve the customer's authorization scope. Unexpected differences block deployment.

For CloudFormation, download the returned template and compare its SHA-256 with the artifact's `version` (`sha256-<hex>`). The digest describes published bytes, not a newer repository template. A mismatch requires fresh requirements and, if it persists, a corrected release manifest; do not edit the template or ignore the mismatch to force the test through. Inspect its parameters, trust and permissions, then deploy those exact reviewed local bytes with the controller's template-body/file option. Do not have CloudFormation fetch the mutable URL again after review. Only use feature parameters supported by that published artifact.

The Terraform artifact's supported features may be narrower than the available catalog. A non-deployable artifact requires a different supported path; do not invent a module version or add unsupported arguments. A Terraform provider resource that registers the role remains the registration owner. The CloudFormation member artifact registers through a callback. For a manually authored role whose controller does not register it, use dry-run and explicit registration after deployment.

The CloudFormation member template bundles baseline read grants. Selecting features in requirements does not remove those grants. Its legacy callback can initially discover all permission-supported capabilities, so the registered feature list may exceed the requested selection. After the callback completes, read the actual registration. If narrowing the desired selection is appropriate to the customer's request, preview that exact binding PATCH, inspect its effects and follow-ups, then apply it with the current ETag. Preserve CloudFormation's ownership of IAM and registration; do not add a duplicate POST. Narrowing desired selection does not revoke bundled IAM permissions or prove that legacy consumers are disabled. Preservation through later callbacks depends on the deployed backend's support for desired selection; reread after a controller update rather than assuming newer writer guards are already deployed.

For AWS `core`, the complete returned managed-policy set (SecurityAudit, AWSSavingsPlansReadOnlyAccess and Billing) is an accepted alternative to the listed legacy action permissions. Do not require both alternatives, add redundant grants, or remove a valid existing alternative solely to match the other. Fresh verification still evaluates access limitations.

Evaluate IAM trust and actual grants, including managed policies, deny statements, permission boundaries and organization controls. A role that can be assumed is only a baseline success. Permission analysis and integration checks are separate. Repair missing permissions in the authoritative source and apply in place rather than creating duplicate roles.

For real-time access, resolve the returned bucket inputs and verify the actual bucket/notification/object checks. These checks can fail because of bucket resource policies even when the role policy appears correct. Callback outcomes, registration state, follow-ups and verification are separate evidence. A parent organization operation or an old healthy record does not prove a new member callback succeeded.

For a new, unregistered AWS role, dry-run can return `authentication.status=unsupported`, reason `aws_broker_requires_registration`, and an unmet `live_identity_gate`. The credential broker needs registration context to assume this role. This specific result does not prove access and cannot be fixed by repeating the dry run. After deploying reviewed IAM and satisfying the requirements prerequisites, explain the limitation and perform the authorized registration: it uses a guarded temporary reservation and checks STS/GetRole before exposing the registration. Existing registered roles can be probed during dry-run. Other failed prerequisites still require repair.

For policy-based features, `feature_health_check` reports the narrower declared-permission or accepted-managed-policy coverage used by existing integrations. `attached_policy_analysis` can still be `partial` when effective access is uncertain. A passing narrower check does not make the whole verification passed. Real-time data and Expert Advice require their separate runtime checks.
